# «Історії принцеси Лілі» / Princess Lily Stories — інтернет-магазин

Невеликий двомовний (uk/en) магазин дитячих книжок: вітрина, кошик без реєстрації, оформлення,
сторінка статусу замовлення, платіжний адаптер, приватна видача PDF, доставка Новою поштою, захищена адмінка.

> **Статус (09.10.2026):** робоча збірка готова до публікації, але **ще не опублікована**: із середовища розробки
> заблоковано доступ до api.vercel.com і api.telegram.org, облікових даних Vercel/Telegram немає (див. «Публікація демо на Vercel»).
> Ціни, справжні PDF, email-провайдер і токени ще не надані — відповідні функції **чесно вимкнені** й показують це
> (книжка «Незабаром», в адмінці — «не налаштовано»). Оплата за замовчуванням — `manual-link` з наданим посиланням monobank і ручною перевіркою.

Це окремий застосунок у теці `princess-lily/` репозиторію (поруч — інший проєкт, його не змінено).

## Стек
- **Next.js 16** (App Router, TypeScript, Turbopack), React 19, Tailwind CSS 4.
- **Kysely** — один код для **SQLite** (розробка) і **PostgreSQL** (production, напр. Supabase). Схема — `src/db/migrate.ts`.
- `jose` (підписаний HttpOnly-cookie сесії), `bcryptjs`, `zod`, `sharp` (зображення).
- Шрифти: Cormorant (заголовки) + Manrope (текст) — обидва OFL, з кирилицею, **локально** через Fontsource.

## Швидкий старт
```bash
cd princess-lily
cp .env.example .env                 # заповніть SESSION_SECRET (openssl rand -base64 32)
npm install
npm run db:setup                     # таблиці + чернетка товару з наданою обкладинкою
npm run admin:create -- you@example.com   # виводить тимчасовий пароль ОДИН раз (або ADMIN_PASSWORD=…)
npm run dev                          # http://localhost:3000 → /uk ; адмінка — /admin
```
Без платіжних/email ключів сайт працює: книжка показується як «Незабаром», оформлення вимкнене.

### Перевірити покупку локально (демо)
```bash
DATABASE_URL=file:./data/demo.db npm run demo:fixtures          # «[DEMO]» товар; відмовляється в production
DATABASE_URL=file:./data/demo.db ADMIN_PASSWORD='Garden-Path-Lantern-2026' npm run admin:create -- owner@example.com
DATABASE_URL=file:./data/demo.db PAYMENT_MODE=provider PAYMENT_PROVIDER=test \
  PAYMENT_WEBHOOK_SECRET=dev_only EMAIL_PROVIDER=outbox npm run dev
CHROMIUM_PATH=… npm run test:e2e                                  # наскрізна перевірка (див. нижче)
```
Тестовий провайдер (`PAYMENT_PROVIDER=test`) і `EMAIL_PROVIDER=outbox` **ігноруються при `NODE_ENV=production`**.

## Сценарій покупки
- На сторінці книжки: «Мова книжки» → «Формат» (лише доступні варіанти) → ціна й наявність оновлюються; до вибору валідного варіанта кнопки неактивні.
- **«Купити зараз»** → `/uk/checkout?buy=<варіант>&qty=N`: оформлюється лише ця книжка, кошик не читається й не змінюється.
- **«Додати в кошик»** → підтвердження з кількістю в кошику; у кошику — окремі рядки мов/форматів, кількість, видалення, «Оформити замовлення».
- Обидва шляхи — та сама серверна перевірка ціни, наявності, доставки й оплати; «До сплати» видно до переходу в банк.
- Оформлення: email, ім’я, прізвище; для друку — телефон, Нова пошта, за бажанням інший одержувач (ім’я, прізвище, телефон).

## Оплата
Режим обирається в **адмінці → Налаштування → Оплата** (`PAYMENT_MODE` — лише значення за замовчуванням):
- **`manual-link`** (типово) — надане посилання `https://send.monobank.ua/7ZH664WCkK` (змінюється в адмінці). Тип посилання й підтримка
  передачі суми **не підтверджені**, тому сума в URL **не дописується**. Замовлення зберігається до переходу на оплату; покупець бачить
  точну суму, кнопки «Скопіювати суму» й «Перейти до оплати», інструкцію ввести суму та номер замовлення, «Я оплатив(ла)» (лише позначка
  «очікує перевірки», **нічого не видає**) і може приватно додати квитанцію. Адміністратор звіряє надходження → «Оплату звірено — підтвердити»
  → видача PDF / відправлення. **Автоматичної видачі в цьому режимі немає** — FAQ і «Доставка й оплата» кажуть «після підтвердження оплати».
- **`mono-acquiring`** — рахунок на кожне замовлення (`POST /api/merchant/invoice/create`: сума в копійках, ccy 980, reference = order_id,
  redirectUrl, webHookUrl → `pageUrl`), вебхук `POST /api/payments/webhook/mono` з перевіркою підпису `X-Sign` (ECDSA, ключ з `/api/merchant/pubkey`)
  і додатковою серверною перевіркою `/api/merchant/invoice/status`. Потрібен `MONOBANK_TOKEN` власниці; без нього режим не активний.
  **⚠️ Реалізовано за публічною документацією, наживо не перевірено** (документацію й API заблоковано в середовищі розробки) — перед
  увімкненням звірте поля з актуальною документацією й проведіть тестовий платіж.
- **`disabled`** — оформлення недоступне.
- Обробка платежів (`src/lib/fulfillment.ts`): невірний підпис → 401; перевірка `order_id`, суми й валюти; ідемпотентність `(provider, event_id)`;
  success-URL з браузера нічого не підтверджує; «оплачено» — лише один раз.

Ціни зберігаються в **копійках** (`integer`), підсумки рахує сервер з каталогу; ціни з браузера ігноруються.
Зміна ціни не змінює вже оформлені замовлення (`order_items` — знімок назви, мови, формату й ціни).

## Видача електронних книжок
- PDF зберігаються в **приватному сховищі** (`PRIVATE_STORAGE=local` → `storage/private/`, або `supabase` → приватний bucket), ніколи не в `public/`.
- Після оплати: лист з **особистими посиланнями з обмеженим строком** (`DOWNLOAD_LINK_TTL_HOURS`, за замовч. 72 год)
  і кількістю завантажень (`DOWNLOAD_MAX_COUNT`, 5). У БД — лише SHA-256 хеші токенів. Скасоване/неоплачене замовлення → посилання не працюють.
- Email-адаптер (`src/lib/email`): `resend` (HTTP API) або `none`. Журнал `email_deliveries`: статус, спроби, остання помилка,
  наступна спроба (5 хв → 30 хв → 2 год → 12 год, до 5 спроб). Дублікати виключені ключем `dedupe_key`.
  В адмінці: «Надіслати лист повторно» і «Створити посилання для ручного надсилання» (коли email не налаштовано).
- **Стан зараз:** email-провайдер і справжні PDF відсутні → у замовленні буде «email не налаштовано», без імітації успіху.

## Доставка (Нова пошта)
Адаптер `src/lib/delivery/nova-poshta.ts`. Без `NOVA_POSHTA_API_KEY` — ручне введення міста та відділення/поштомату
з підписами полів; з ключем — підказки з API (`getCities` / `getWarehouses`; **не перевірено без ключа**).
Тариф не розраховується: «за тарифами перевізника, оплачує покупець». Статус доставки окремий від статусу оплати;
ТТН вводить адміністратор, покупець бачить її на сторінці статусу.

  сума, спосіб і стан оплати, доставка й відділення, стан відправлення й ТТН; позначки **PDF / Друк / Змішане**.

  формату й стану замовлення; пагінація 25/50/100.
- Експорт **поточного відфільтрованого списку** у справжній `.xlsx` (ExcelJS: українські заголовки, київський час, суми числом, автофільтр,
  захист від формул — текст на `= + - @` екранується) і `.pdf` (A4 landscape, кирилиця DejaVu Sans, переноси, повтор шапки на кожній сторінці,
  підсумок кількості й суми). Лише адмінам через сервер (`/admin/orders-export`, без входу 401), без кешу, з записом у журнал.
- Картка замовлення: час створення/оплати, позиції зі збереженою ціною, покупець (ім’я, прізвище, телефон, email), окремо одержувач, відправник
  (заповнює магазин), коментар, внутрішня примітка, ТТН; оплата — метод, ID рахунку провайдера, сума, час, хто й коли перевірив; приватні
  квитанції (покупця або адміна; лише PDF/JPG/PNG/WebP за вмістом файлу, до 5/10 МБ, перегляд лише адміну з журналом); **хронологія** змін
  статусів замовлення/оплати/PDF/доставки з відповідальним; дозволені переходи стану замовлення (Нове → В роботі → Виконано, Скасовано);
  стан Telegram-сповіщень. Фальшиві квитанції не генеруються; посилання send.monobank не вважається підтвердженням.

## Telegram
Див. **docs/TELEGRAM.md** (інструкція для власниці). Повідомлення про нове збережене замовлення (після відповіді покупцю — не блокує checkout)
і окреме — про **підтверджену** оплату. Outbox `notifications` зі станом, спробами, помилкою; ідемпотентність без дублів; повтори з backoff
(`npm run notify:retry` / `/api/cron/retry` / кнопка в адмінці). Без `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` замовлення зберігаються, а адмінка показує «не налаштовано».
**Реальну доставку повідомлення в чат бота не перевірено**: api.telegram.org заблоковано в середовищі розробки, токена немає.

## Адмінка `/admin`
- Вхід email+пароль; сесія — підписаний HttpOnly cookie (12 год, SameSite=Strict) з перевіркою по БД (неактивний користувач / зміна пароля анулює сесії).
- **Кожна** сторінка, server action і API адмінки викликає `requireAdmin()`/`getAdmin()` на сервері. Ролі: `owner` (усе) і `staff` (без налаштувань, журналу, завантаження PDF).
- Пароль за замовчуванням не створюється; прості паролі (`admin`, частина email, < 12 символів) відхиляються.
- Ліміт спроб входу: 10/15 хв з IP і 8/15 хв на обліковий запис.
- Функції: товари (статус: чернетка / незабаром / опубліковано), переклади uk/en (з позначкою «переклад погоджено»), обкладинки,
  варіанти «мова книжки × формат», ціни, залишки, примітка про надходження, приватне завантаження PDF; замовлення (пошук, фільтр,
  деталі, події платежу, ручне підтвердження оплати, скасування, доставка/ТТН, повторне надсилання PDF, нотатки); звернення;
  налаштування контактів і платіжного посилання; зміна пароля; **журнал дій** (`audit_log`).
- Зручно з телефона: нижня панель розділів, поля ≥ 44 px.

Товар продається лише якщо: статус «Опубліковано», варіант увімкнено, ціна > 0, є PDF (для PDF) або залишок (для друку).

## Публікація демо на Vercel (безкоштовна адреса `*.vercel.app`)
Потрібні: доступ до Vercel (акаунт власниці/розробника) і безкоштовна база Postgres (Supabase або Neon). SQLite на Vercel не працює
(файлова система лише для читання), тому для публічної адреси потрібен Postgres.
1. Supabase → New project → Settings → Database → Connection string (URI, **Session pooler**) → це `DATABASE_URL`.
2. Vercel → Add New Project → імпорт репозиторію `helen556/gritsweet` → **Root Directory: `princess-lily`** (Framework: Next.js).
3. Environment Variables (Production): `DATABASE_URL`, `SESSION_SECRET` (`openssl rand -base64 32`), `APP_URL=https://<проєкт>.vercel.app`,
   `CRON_SECRET`; за наявності — `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`; для PDF-сховища — `PRIVATE_STORAGE=supabase`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`;
   `UPLOADS_DIR=/tmp/uploads` (завантажені з адмінки обкладинки на Vercel тимчасові — для постійних потрібне інше сховище).
4. Deploy. `vercel.json` запускає `npm run vercel-build` (= `db:setup` + `next build`): таблиці й чернетка товару створюються автоматично.
5. Виконати `supabase/policies.sql` у Supabase SQL Editor (RLS, приватний bucket).
6. Створити власницю: локально `DATABASE_URL=<той самий> npm run admin:create -- email@… owner` (тимчасовий пароль виводиться один раз).
7. Перевірити `https://<проєкт>.vercel.app/uk` на телефоні й комп’ютері, тестове замовлення (коли буде товар із ціною) і Telegram.
Альтернатива без Vercel: будь-який Node-хостинг з постійним диском (`npm ci && npm run build && npm run db:setup && npm start`, SQLite можна).

## Production (Supabase / Postgres)
1. Postgres: `DATABASE_URL=postgres://…` (Supabase → Connection string). `npm run db:setup`.
2. Виконати `supabase/policies.sql`: RLS увімкнено на всіх таблицях, доступ для `anon/authenticated` заборонено;
   приватний bucket `private-books` (лише PDF, до 100 МБ). `PRIVATE_STORAGE=supabase`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`.
3. Обкладинки, завантажені з адмінки, пишуться в `UPLOADS_DIR` (локальний диск). Для serverless-хостингу без постійного диска
   потрібен постійний том або перенесення обкладинок у публічний bucket (не реалізовано).
4. `APP_URL=https://<домен>` (canonical, hreflang, sitemap, посилання в листах).
5. Cron: `npm run email:retry` кожні 10 хв.

## SEO, доступність, швидкість
- Маршрути `/uk` (за замовчуванням) і `/en`, окремі словники (`src/i18n`), перемикач зберігає сторінку й параметри; мова сайту ≠ мова книжки.
- Унікальні title/description, canonical, hreflang uk/en/x-default, `sitemap.xml`, `robots.txt`; noindex для адмінки, кошика, оформлення,
  замовлень, завантажень і чернеток оферти/політики. Open Graph — наявна обкладинка. Schema.org Product/Offer — лише для опублікованих товарів з ціною, без рейтингів.
- Перед запуском: реальний домен у `APP_URL`; верифікацію Google Search Console додати після отримання (не вигадано).
- Аналітика: `NEXT_PUBLIC_ANALYTICS_PROVIDER=plausible` + `NEXT_PUBLIC_ANALYTICS_DOMAIN` (без cookie й персональних даних); без змінних — нічого не завантажується.
- LCP — постер hero з `preload`/`fetchpriority=high`; відео підвантажується після гідратації; CSS вбудовано (`inlineCss`); стабільні розміри медіа.

## Візуальні ефекти й композиція (правки від 09.10.2026)
- **Повноекранний hero** (100svh) на desktop і mobile з відео без обрізання ключових моментів і знака Kling; назва — справжній `h1` на легкій
  CSS-хмаринці; сценарій «пил → хмаринка → назва → слоган і CTA "До книжок"» до ~2 с, раз за сесію (деталі — docs/ASSETS.md).
- **Вступ зоряним пилом** (`StardustIntro.tsx`): перламутрова «хмаринка» з м’яких плям і мерехтливих частинок розходиться за ~1 с; canvas, `pointer-events:none`, `aria-hidden`.
- **Слід курсора** (`CursorTrail.tsx`): лише fine pointer; пул ≤ 70 (≤ 36 на слабких пристроях + адаптивне зниження), DPR ≤ 1.5, без setState на pointermove;
  цикл зупиняється без частинок і при прихованій вкладці. На touch — лише короткий блиск CTA.
- **Фон з глибиною** (`Ambient.tsx`): великі молочні/перламутрові/шавлієві плями світла, що плавно перетікають між секціями (без прямокутних смуг),

## Потрібно від власниці
Доступ до Vercel (або іншого хостингу) і безкоштовна база Postgres для публічної адреси; `TELEGRAM_BOT_TOKEN` (ввести в змінні середовища самостійно) і chat_id;
за бажанням — підключений еквайринг monobank і merchant token; каталог і ціни; справжні PDF кожної мовної версії; переклади назв/описів (англійське видання цієї книжки не підтверджене);
параметри видань (сторінки, розмір, обкладинка) — якщо потрібні; контакти й реквізити продавця (оферта, політика конфіденційності —
зараз чернетки з позначками); умови повернення; домен; вибір платіжного провайдера та email-сервісу й їхні ключі;
(за бажанням) ключ API Нової пошти; рішення щодо хостингу (постійний диск або Supabase).
