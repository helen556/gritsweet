# Grid Sweet Life — сайт кондитерки Дар’ї (Кропивницький)

Публічний сайт + конструктор заявки + захищена адмінка `/admin`.

**Стек:** Next.js 16 (App Router, TypeScript), Tailwind 4, Kysely (SQLite для розробки / PostgreSQL для продакшену — той самий код), framer-motion, sharp, jose + bcrypt.

> Prisma не використано: у середовищі, де збирався проєкт, її рушій не завантажується. Kysely працює без бінарних залежностей.

---

## 1. Запуск локально

```bash
cp .env.example .env        # заповніть SESSION_SECRET, ADMIN_EMAIL, ADMIN_INITIAL_PASSWORD
npm install
npm run db:setup            # створює таблиці, прайс із ТЗ, тексти й адміністратора
npm run dev                 # http://localhost:3000, адмінка — /admin
```

Перевірки: `npm test` (прайс і телефон), `npx tsx --import ./scripts/shim/register.mjs scripts/smoke.ts` (ліміт дня, дублі, знімок прайсу на тестових даних).

## 2. Змінні середовища

| Змінна | Призначення |
|---|---|
| `DATABASE_URL` | `file:./data/dev.db` (SQLite) або `postgres://…` (Supabase/Neon/власний Postgres) |
| `SESSION_SECRET` | ≥ 32 випадкових символи: `openssl rand -base64 32` |
| `ADMIN_EMAIL`, `ADMIN_INITIAL_PASSWORD` | Використовуються лише один раз при `db:setup`, якщо адміністратора ще немає |
| `APP_URL` | Публічна адреса сайту (для посилань відновлення пароля) |
| `PRIVATE_STORAGE_DIR` | Тека для референсів клієнтів (за замовчуванням `storage/private`) |

Секретів у клієнтському коді немає; `.env` у `.gitignore`.

## 3. Розгортання (потрібне ваше рішення)

Сайт **не опублікований** — це ваша дія. Проєкт пише файли на диск (референси, фото), тому потрібен хостинг із постійним диском **або** заміна сховища:

- **Найпростіше:** VPS/Docker (Hetzner, DigitalOcean тощо): `npm ci && npm run build && npm run db:setup && npm start`. Postgres або SQLite на диску; теки `data/`, `storage/private/`, `public/uploads/` — на постійному томі.
- **Vercel + Supabase (підтримується):** див. розділ 11.

Після розгортання: змініть пароль у «Тексти та налаштування», встановіть `APP_URL`.

## 4. Резервне копіювання та відновлення

- SQLite: `npm run db:backup` → копія в `backups/`. Також копіюйте `storage/private/` і `public/uploads/`.
- PostgreSQL: `pg_dump "$DATABASE_URL" > backups/$(date +%F).sql`; відновлення `psql "$DATABASE_URL" < файл.sql`.
- Відновлення SQLite: зупинити сервер, покласти файл копії як `data/dev.db`, запустити.

## 5. Інструкція для Дар’ї (з телефона)

**Увійти.** Відкрийте `адреса-сайту/admin`, введіть email і пароль. Знизу — вкладки розділів.

**Забула пароль.** Email-розсилки немає. Той, хто адмініструє сервер, виконує `npm run admin:reset -- ваш@email` і надсилає вам одноразове посилання (діє 30 хв).

**Закрити дату або вихідні.** Календар → «Закрити або відкрити дні» → дата «Від» (і «До» для діапазону) → Закрити → Застосувати. Підтверджені замовлення на ці дні **не скасовуються** — з’явиться попередження. Натисніть день у сітці, щоб додати приватну примітку або ліміт підтверджених на день (порожньо = без ліміту).

**Змінити ціну.** Каталог → «Змінити» біля позиції → тип ціни (Фіксована / Діапазон / «Від» / «Уточнюйте») і суми в грн → Зберегти позицію. Старі заявки залишаються зі своїм прайсом.

**Додати позицію.** Каталог → у потрібній категорії «+ Додати позицію» → назва, одиниця (кг/штука/коробочка/букет), тип ціни, мінімум, начинки (по одній у рядку), фото зі списку → Додати. Фото спершу завантажуються у «Фото». «Приховати» — тимчасово зняти з сайту, «В архів» — прибрати назавжди без руйнування старих заявок.

**Опрацювати заявку.** Огляд або Заявки → відкрити → «Подзвонити» → після розмови: «→ Уточнення» або «→ Підтверджена» (лише ваша ручна дія; клієнту нічого не надсилається автоматично). Впишіть остаточну ціну й нотатки → Зберегти. «Перенести» змінює дату зі збереженням історії. Відхилити/Скасувати — з підтвердженням.

**Мінімальна партія капкейків.** Тексти та налаштування → «Правила замовлення». Поки не встановлена — на сайті кількість позначена як побажання.

**Фото «Про мене».** Фото → завантажити портрет → Тексти → «Фото “Про мене”» → обрати → Зберегти.

## 6. Безпека (що реалізовано)

- Сесія — підписаний HttpOnly-cookie (12 год), паролі — bcrypt; сталий час відповіді при невірному email.
- Публічної реєстрації немає; відновлення — лише через команду на сервері.
- Кожна адмін-сторінка і server action викликає `requireAdmin()`.
- Відвідувач бачить лише опубліковані позиції та список закритих дат (`/api/availability`); заявки, телефони, примітки, ліміти анонімно недоступні.
- Ціна, кількість, мінімум, дата й доступність позиції перевіряються на сервері; сума з браузера не використовується.
- Ідемпотентний ключ заявки + унікальний індекс — захист від подвійного надсилання; honeypot; ліміт 5 заявок / 10 хв з IP (IP зберігається як хеш).
- Завантаження: лише зображення до 5 МБ, перекодування у WebP (прибирає метадані). Референси — у приватній теці, віддаються тільки авторизованому через `/admin/reference/…`.
- Логи не містять телефонів та імен. Заголовки X-Frame-Options, nosniff, noindex для `/admin`.

## 7. Що не підключено / потребує рішення

- Хостинг, домен, продакшен-БД — не налаштовані.
- Повідомлення клієнтам (SMS/Telegram) — немає, зв’язок вручну.
- Email для відновлення пароля — немає (є команда на сервері).
- Онлайн-оплата — не реалізована (за ТЗ).
- Файлове сховище для serverless-хостингу — потрібна адаптація.
- Фото Дар’ї — не передано, слот є в адмінці.
- Політика обробки даних — чернетка: підтвердити володільця, контакт і строк зберігання.
- Ліміт дня в SQLite: захист від гонки гарантований для одного процесу; для кількох інстансів використовуйте PostgreSQL (там `SELECT … FOR UPDATE`).

## 8. Відгуки та Instagram (доповнення)

- Секція «Ваші відгуки — моя найбільша радість» після «Про мене»: карусель скриншотів (свайп, Назад/Далі, індикатор, без автопрокрутки), лайтбокс із закриттям кнопкою/Escape, стрілками між слайдами, пасткою фокуса й поверненням фокуса.
- Опубліковано 7 слайдів (IMG_8904, 8900 + 8901 як продовження, 8903, 8902, 8905, 8899). Нікнейми й аватарки запікселені **в самих файлах** (`public/uploads/reviews/`); оригінали — лише в `storage/private/reviews/` і доступні тільки адміністратору через `/admin/review-image/…`.
- Чернетки (не опубліковано, у публічній папці відсутні): IMG_8895, 8894, 8897 (фото клієнтів), 8898 та 8896 (кадри з дітьми — потрібен дозвіл).
- Адмінка → «Відгуки»: завантаження (завжди чернетка), перегляд, порядок ↑↓, публікація/приховування (публікація можлива лише з позначкою «дозвіл перевірено»), видалення з підтвердженням, опис для доступності. Приховування прибирає файл із публічної папки.
- Instagram: запрошення з кнопкою після галереї зефірних квітів і компактне посилання під відгуками; усі посилання `target="_blank" rel="noopener noreferrer"`. Стрічка/API не підключаються.
- Скрипт `scripts/prepare-reviews.ts` — те, чим готувалися стартові файли (маски задані вручну для кожного скриншота). Для нових скриншотів анонімізуйте зображення перед завантаженням або завантажте вже оброблену копію.

## 9. Фото Дар’ї, категорії, галерея «Мої роботи» (доповнення)

- Фото Дар’ї з букетом обрізано лише знизу (чорна смуга), обличчя не змінювалось; підключено до «Про мене» (`about_photo`), можна замінити в «Текстах».
- Категорії з фото: Торти (вишневий торт), Зефір (зефірні звірята), Зефірні квіти (рожевий букет). **Бенто** та **Капкейки** без фото — серед надісланих немає відповідних; додайте в «Фото» → «Каталог» → Редагувати категорію. До конкретних смаків фото не прив’язувались (склад на фото не підтверджено).
- Секція «Мої роботи» після «Зефірних квітів»: 16 фото, сітка з лайтбоксом (Escape, стрілки, фокус). Instagram-запрошення перенесено під цю галерею.
- Адмінка → «Фото»: підпис, порядок, «У галерею / Прибрати з галереї», видалення (заборонено, якщо фото використовується в каталозі).
- Дублікати серед надісланих (коробочка та сфера з метеликами) і скриншот сайту не додавались.

## 10. Бенто-поєднання та склад на вибір (доповнення)

- Категорія «Бенто»: 22 приклади поєднань (назва = складові, опис «Приклад поєднання… Склад можна змінити в заявці») + «Бенто за вашим складом». Усі — «Вартість уточнюйте». Стара єдина позиція «Бенто-торт» архівована.
- У «Тортах» додано «Торт за вашим складом» (уточнюйте, від 1 кг).
- Склад на вибір (бісквіт*, курд, конфітюр, мус, карамель, хрусткий прошарок — за списком Дар’ї) показується в конструкторі на кроці «Деталі»; бісквіт обов’язковий, решта — за бажанням. Вибір зберігається у знімку заявки та видимий в адмінці.
- Сервер перевіряє, що обрані варіанти існують у групах позиції.
- Адмінка → Каталог → позиція → поле «Склад на вибір»: один рядок = група, формат `*Назва: варіант, варіант` (зірочка = обов’язково). Можна додати склад будь-якій позиції, у т.ч. звичайним тортам.


## 11. Розгортання на Vercel + Supabase (покроково)

Проєкт підтримує два режими без змін у коді: локально — SQLite + диск; на Vercel — Supabase Postgres + Supabase Storage (бакети `public` і `private` створюються автоматично при першому `db:setup`).

**A. Supabase (5 хв)**
1. supabase.com → New project. Запам'ятайте пароль бази.
2. Project Settings → Database → Connection string → вкладка **Transaction pooler** (порт 6543) → скопіюйте `postgres://…` і підставте пароль. Це `DATABASE_URL`.
3. Project Settings → API → скопіюйте **Project URL** (`SUPABASE_URL`) і **service_role** key (`SUPABASE_SERVICE_ROLE_KEY`). Це секретний ключ — лише у змінні Vercel, нікуди більше.

**B. Vercel (5 хв)**
1. Завантажте проєкт (zip або GitHub). Framework: Next.js. Build Command можна не чіпати — використовується скрипт `vercel-build` (`npm run db:setup && next build`), який створює таблиці, прайс і адміністратора.
2. Settings → Environment Variables (Production і Preview):
   - `DATABASE_URL` — рядок із кроку A2
   - `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` — з кроку A3
   - `SESSION_SECRET` — `openssl rand -base64 32` (або будь-які 40+ випадкових символів)
   - `ADMIN_EMAIL`, `ADMIN_INITIAL_PASSWORD` — для першого входу
   - `APP_URL` — адреса сайту, напр. `https://grid-sweet-life.vercel.app`
3. Deploy (Redeploy, якщо змінні додано після першого деплою).
4. Відкрийте `/admin`, увійдіть, змініть пароль у «Тексти та налаштування».

**C. Оригінали відгуків (один раз, локально)**
Чернетки відгуків (нікнейми, діти) лежать у `storage/private/reviews` і не потрапляють на Vercel. Щоб їх можна було публікувати з адмінки, залийте їх у приватний бакет з комп'ютера:
```bash
# у .env локально тимчасово вкажіть SUPABASE_URL і SUPABASE_SERVICE_ROLE_KEY
npm run storage:sync
```
Без цього кроку 7 уже опублікованих відгуків працюють (файли статичні в `public/`), а чернетки при спробі опублікувати скажуть «Оригінал не знайдено — завантажте ще раз».

**Що де зберігається на Vercel**
- База: Supabase Postgres (заявки, каталог, календар, відгуки, адміністратор).
- Стартові фото (`/images`, `/uploads/works`, `/uploads/reviews`) — статично з репозиторію.
- Нові фото товарів і галереї → бакет `public`, папка `photos/`.
- Референси клієнтів → бакет `private`, `references/` (віддаються лише адміністратору).
- Нові скриншоти відгуків → `private/reviews/`, після публікації копія в `public/reviews/`.

**Резервні копії:** Supabase робить бекапи бази автоматично (Dashboard → Database → Backups); для Storage скачайте бакети через Dashboard або `pg_dump` + Storage API.

**Перевірено:** повний цикл (заявка з референсом → адмінка → статус, календар, зміна ціни, завантаження фото, перегляд відгуків) на реальному PostgreSQL 16. Supabase Storage у середовищі розробки недоступний — код написаний за офіційним SDK, але перший запуск на Vercel варто перевірити: завантажте тестове фото в «Фото» і референс у тестовій заявці.
